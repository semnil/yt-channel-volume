# Design

> English: [design.md](design.md)

コードが従っている決定を、1 つの決定につき 1 項目で書く。各項目は、先頭の太字の言葉で名指す。各スクリプトが何をするかは [architecture.ja.md](architecture.ja.md) にあり、ゲインが変わる道筋のすべてと、そのうちどれがチャンネルの設定を保存するかは [gain-change-and-save.ja.md](gain-change-and-save.ja.md) にある。閉じた判断と、その理由、覆す条件は [decisions/](decisions/) にある。

## Key design decisions

- **GainNode, not HTMLMediaElement.volume**: volume プロパティは 1.0 が上限。GainNode なら 0.0–6.0 (0–600%) を扱える
- **Per-channel, per-type automatic LUFS apply**: 今の種別に対応する `autoApplyLoudnessVideo` / `autoApplyLoudnessLive` が true で、loudnessDb が取れたとき、Target LUFS から計算したその動画のためのゲインを適用し、素の音声の版について計算したゲインを、その種別のゲインとして `channelVolumes` に保存する (「A stored gain is held against the base rendition」を参照)。loudness を検出できないときと、Auto が OFF のときは、その保存ゲインを使う。ライブのレベルは loudnessDb より先に使う (「A live stream's own level」を参照)。古い形式の `autoApplyLoudness` は、両方の種別で true として読む
- **Auto and manual do not get separate gains**: どちらも `channelVolumes.{id}.gainVideo` / `gainLive` の 1 つの値に保存する。Auto を ON / OFF に切り替えても、LUFS を検出できない動画にかかるゲインは変わらない
- **Turning Auto on stores the gain it plays, with the flag**: `enabled: true` の `setAutoApplyLoudness` は、その種別のレベルが分かっているとき (手元のライブのレベル `readLiveLkfs`。これが Auto の `currentLiveLkfs` になる。無ければ `currentLoudnessDb`)、Auto のゲインをすぐに鳴らし、それを `autoApply: true` と一緒に 1 回の `saveChannelGain` で書く。書く値は「チャンネルに適用」が保存する値と同じ: ライブのレベルのゲインは印なし (`heldAgainstPlain: false`。書き込みが届いたら `liveSaveBaseline` を入れるので、次に来る追従が同じゲインをもう一度保存しない)、動画は `calcStoredGainFromLoudness()` の値で、素の音声の版のレベルが分かっているときは印を付ける。書き込みが失敗したときは、保存ゲインを戻して (`restoreGainAfterFailedSave()`) から、ポップアップに `{ ok: false }` を返す。レベルが分かっていないときと、Auto を OFF にするときは、フラグだけを書く (`saveChannelAutoApply`)。ゲインは、後に続く `applyPreferredGain()` を待たない: その適用がエントリを読んでいる間に書き込みの変更通知が届くことがあり、そのときはリビジョンの確認がその適用を捨てる
- **All-channel defaults and individual settings**: `autoApplyLoudnessVideoDefault` / `autoApplyLoudnessLiveDefault` は、個別の Auto のフラグが無い種別に効く。手動の保存 (「チャンネルに適用」 / Manual Volume) は、そのときの Auto の状態を個別のフラグとして書くので、そのチャンネルはそれ以降、全チャンネル共通の既定値に従わなくなる。Auto 自身のゲインの保存はフラグを書かず、チャンネルは既定値に従い続ける。既定値を変えても `channelVolumes` は書き換えない
- **MAIN world / ISOLATED world split**: YouTube の CSP はインラインのスクリプトを禁じているので、loudnessDb の取り出しは `page-bridge.js` (MAIN world、`document_start`) で走る
- **The level of the rendition the player plays**: 1 本の動画は音声の版をいくつも持ち、それぞれが自分のレベルを持つ — 音声トラックごと (元の音声と吹き替え) にあり、1 つのトラックの中にも、素の版、Stable Volume (DRC) の版 (adaptive format の `isDrc`)、Voice Boost の版がある — そして `playerConfig.audioConfig.loudnessDb` が表すのは、そのうちの 1 つだけ。プレイヤーの統計情報 (stats for nerds) の音量の行 (`movie_player.getStatsForNerds().volume`。例: `100%/100% DRC (cont.-14.3dB tgt.-14.0dB)`) は、どの設定がそれを選んだにせよ、再生している音声の版の絶対値のレベル (LKFS) を `cont.` で名指す。ブリッジの返事はどれも — `define`、`fetch`、content.js の問い合わせへの返事、`onPlaybackAudioChange` への返事 — `preferPlayingLevel` を通る。これは、統計情報がフォーマットを名指し (`codecs` は、プレイヤーがフォーマットを選ぶまで空で、そのとき `cont.` は応答自身のレベルを運ぶ)、かつ URL の指す動画を名指している (`video_id_and_cpn` は `<videoId> / <cpn>`) ときに、そのレベルから応答の `loudnessTargetLkfs` を引いた値を取る。プレイヤーはそのレベルを 0.1 dB に丸めて描く (音声の版の `trackAbsoluteLoudnessLkfs` の `toFixed(1)`)。応答が表す音声の版 (`audioConfig` と各 adaptive format) のうち、絶対値のレベルを丸めると名指されたレベルになるものが、どれも同じ 1 つの `loudnessDb` を持つときは、応答が与えるその `loudnessDb` をそのまま答えにする (`playingLevel`)。そうでないときは、名指されたレベルから目標を引いた値を答えにする。それまでは答えは応答から取り、250 ms ごとに、最大 40 回、プレイヤーをもう一度見て、プレイヤーが初めてレベルを名指したときにもう一度返事をする (source は `playing`)。プレイヤーのレベルを運ぶ返事は、見直しを終わらせる。配信中のライブは `cont.` のレベルを名指さない。名指すのは `live.` で、これは `liveLkfs` として返事と一緒に行き、同じく見直しを終わらせる (「A live stream's own level」を参照)。だから、プレイヤーがレベルを名指した後に届いた応答は、どの経路で届いても、そのレベルを置き換えない。この行はプレイヤーが表示のために描く文字列で、この形で読めない行のときは、答えを応答に任せる。応答から取るとき (統計情報で決まらない返事のすべて) は、プレイヤーの Stable Volume の設定が ON なら、応答に `isDrc` のフォーマットの `loudnessDb` があればそれを取り、無ければ `audioConfig` のものを取る。設定は `movie_player.getDrcUserPreference()` から読み、次に、プレイヤーが localStorage に持つ `yt-player-drc-pref` のエントリ (`{ data, expiration }`。期限の切れたエントリは無いものとする) から読む。どちらも 0 か 1 を答えないときは ON として扱う (プレイヤー自身の既定)。プレイヤーは、音声の版が変わったことを `movie_player` の `onPlaybackAudioChange` で知らせる。ブリッジはプレイヤーの要素 1 つにつき 1 回だけ聞き始め (プレイヤーは `document_start` にはまだ無いので、content.js が最初に問い合わせたときに付ける)、URL の指す動画についてもう一度返事をする (source は `audio-change`)。content.js は、同じ動画の新しいレベルをほかのレベルと同じように取り、Auto を適用し直す
- **A stored gain is held against the base rendition**: `gainVideoPlain` / `gainLivePlain: true` と並んで保存された `gainVideo` / `gainLive` は、再生中の音声の版ではなく、`audioConfig` が表す素の音声の版 (`baseLoudnessDb`) のためのゲイン。content.js が保存するゲインは、そのとき素の音声の版のレベルが分かっていれば印を運ぶ (`saveChannelGain` の `heldAgainstPlain`)。印の無いゲイン — そのレベルが分からないとき (配信中のライブ) に保存されたもの、印ができる前に保存されたもの、古い形式のキーから取り込んだもの — は、どの音声の版が再生されていてもそのままの値で鳴り、レベルが分かっているときのその種別の保存が印を付けるまで続く。Auto と「チャンネルに適用」は `calcGain(baseLoudnessDb)` を保存し、`calcGain(loudnessDb)` を鳴らす。ライブのレベルから求めたゲインは印なしで保存し、そのままの値で鳴らす。手動のゲインは、選んだとおりに鳴らし、`renditionGainRatio(loudnessDb, baseLoudnessDb)` で割って保存する。印の付いた保存ゲインは、それを掛けて鳴らす (`applyPreferredGain`、タブ間の同期)。比率は `10^((effectiveLufs(base) - effectiveLufs(playing)) / 20)` で、`effectiveLufs` は YouTube 自身の減衰の後のレベル。だから、持ち越したゲインは両方の音声の版を同じ 1 つのレベルで鳴らす。レベルが無いとき (配信中のライブ。安定した音声の版も無い) は、保存ゲインをそのままの値で鳴らし、何も保存されていないチャンネルは、何が再生されていても 1.0 のまま。素の版のレベルが分からないときは、再生中のレベルがその代わりになる。保存する値は 0–6 (600%) に収める (`playingGainToStored` の `clampGain`) ので、より大きい音の版の上で選んだゲインは、素の音声の版でのゲインが 6.0 を超えるときは 6.0 として保存され、読み戻すと、選んだレベルより小さく鳴る。鳴らす値は `commitGain` が切りそろえる
- **A live stream's own level**: 配信中のライブでは、プレイヤーの音量の行は `live.<LKFS>dB` を名指す。条件は `cont.` と同じ (フォーマットが名指されていること、URL の指す動画であること。プレロール広告は別の動画を名指すので取らない)。ブリッジはこれを、応答のレベルの隣に `liveLkfs` として送り、`loudnessDb` には決して混ぜない。これは YouTube が正規化していない絶対値のレベルとして取るので、`calcLiveGain` はそのままの値で Target LUFS に合わせ、`effectiveLufs` は当てない。見ている種別で Auto が ON のとき、Auto がゲインを適用するすべての場所で、これが loudnessDb より先になる: ブリッジのメッセージ、`applyPreferredGain`、タブ間の同期 (ここでは、このタブのライブのレベルが、別のタブが保存したゲインより先になる)。ブリッジのメッセージはどれもこれを置き換えるので、これの無いメッセージはこれを取り下げ、保存ゲインがまた鳴る。`LEVEL_FLOOR_LKFS` (-45.6 LUFS: 音の無い配信では音量の行が `live.-10000.0dB` を名指す。Target LUFS の最小の -30 から、最大のゲインの +15.56 dB を引くと -45.56) 以下のレベルは、完全な返事で届いても (`levelAboveFloor`)、ライブのレベルの読み取りで届いても、無いものとして数える。読み取りのときは、完全な返事がそれを名指したときと同じく、手元のレベルと Auto のレベルを取り下げる。そのとき Loudness は測らず、表示もせず、行がレベルを名指していないときと同じく、保存ゲインが鳴る。その種別で Auto が ON で、watch ページにいて、配信が配信中 (`isLiveNow`) か手元にライブのレベルがある間、`syncLiveFollow` は 1 秒のタイマーを 1 つ持ち (`AUTO_FOLLOW_INTERVAL_MS`)、ブリッジへもう一度問い合わせる。その返事は、ほかの返事と同じくメッセージのハンドラーを通る。この条件は、適用のたび、ナビゲーションのとき、表示状態が変わったとき、タイマーのたびに見直す。だから、アーカイブ (配信中でなく、ライブのレベルも無い) には追従せず、配信中のプレミア公開には、動画の Auto の下で追従する。何を保存するかは、適用とは別に `evaluateLiveSave` が決める: ある動画と種別についての最初のライブのゲインと、その後は、このページがその同じ動画と種別について最後に保存したゲインからの動き (`gainChangeDb`。比べる前に、プレイヤーがレベルを名指す刻みの 0.1 dB に丸める) が 1 dB 以上のゲインを、その種別の枠に、印も Auto のフラグも付けずに保存する (Auto 自身の保存で、チャンネルは既定値に従い続ける)。量って保存するのはレベルの求めるゲインで、鳴っているゲインがそれより小さい間 — スライダーのプレビューがそれを押さえている間 — は、何も保存しない (理由は `held under the level`)。最後の保存は `liveSaveBaseline` = `{ videoId, videoType, gain }` として持つ: 種別ごとに自分の枠へ保存するので、ページがその配信を別の種別と名指していた間の保存は、この種別の保存の物差しにならず、この種別での最初の評価は最初の保存になる。旧形式の取り込みが届く前、動画が一時停止かミュートのタブ、保存が出ている間は、何も保存しない。保存が失敗すると、比較は元のところに残るので、次の評価がもう一度試す。ライブのレベルは「LUFS が検出された」と数える: Auto が ON なら手動の操作を取り上げ、Auto が OFF なら「チャンネルに適用」がそのゲインを、印なしで、Auto の状態を明示のフラグとして保存する。ポップアップはこれを Loudness として表示し、Suggested をそこから求める (使うのは手元のレベルで、ポップアップ自身の読み取りが Auto のレベルより先へ進めることがある。[architecture.ja.md](architecture.ja.md) の「Live level read for the popup」を参照)
- **`perceptualLoudnessDb` is read as an absolute level**: `audioConfig` に `loudnessDb` が無いとき、`perceptualLoudnessDb` から `loudnessTargetLkfs` を引いた値がその代わりになる。目標が無ければ、レベルは無い
- **Three routes to loudnessDb**: (1) `Object.defineProperty` が、変数が設定されるのを検出する、(2) fetch フック (`/youtubei/v1/player`)、(3) YouTube のプレイヤーの内部の DOM のデータ (`ytd-watch-flexy.__data` / `movie_player.getPlayerResponse`)
- **Filling in isLiveNow**: `_capturedResp` の `isLiveNow` はページの読み込みの時点で固定されているので、request のハンドラーは、配信が始まったかどうかをページ自身の応答に尋ねる (待機 → 配信開始の遷移をカバーする)。値は、URL の指す動画を名指す答えのうち、いちばん新しいものから取る: `movie_player.getPlayerResponse()`、次に `ytd-watch-flexy` (ページが組み立てられたときの応答を持つ)、次に読み込みのときから持っているもの、の順。その `isLive` をそのまま使うので、終わった配信は、タブが離れるのを待たずにバッジを下ろす。これは、レベルがどの答えから来たかに関係なく走る: SPA ナビゲーションの後、読み込みのときから持っているものは、タブがもう離れた動画を名指していて、レベルは代わりにページから来る。content.js の `forceDetect` (ポップアップを開いたとき) はブリッジへもう一度問い合わせ、応答が `currentIsLiveNow` を更新したときは、ポップアップが次の問い合わせでそれを描く
- **videoId filter**: fetch フックは、ほかの動画のための先読みの応答と、`videoDetails` で動画を名指していない応答を捨てる (ライブ配信では `/youtubei/v1/player/ad_break` がそのように答え、それを答えとして取ると、次の答えが来るまで配信が動画になっていた)
- **A page fetch nothing handles**: Chrome は、ページのリクエストから出た、誰も処理しない rejection を、そのリクエストが通った `window.fetch` のラッパーに対して報告し、拡張機能のエラーの一覧に `Uncaught (in promise) TypeError: Failed to fetch` を記録する。`isWatchPage()` が成り立つ間に出すリクエストは `requestMadeOnWatchPage` を通して出し、Chrome が出せなかったリクエストの TypeError は、その呼び出しのスタックを運ぶ。ブリッジの `unhandledrejection` リスナーが既定の動作を止めるのは、`Failed to fetch` と読める `TypeError` で、スタックに `at requestMadeOnWatchPage (chrome-extension://` のフレームがあるものだけ。これは、ページに渡される promise にも、そこからつないだ promise や await した promise にも届き、どちらにも何も付けない。ページ自身の promise が同じエラーで reject されたとき、別のページで出したリクエスト (どのページで失敗しても)、ほかの理由 (abort を含む) で失敗したリクエストは、前と同じく、誰も処理しない rejection を上げる。`Error.stackTraceLimit` を 0 にしているページでの失敗も同じ (そのスタックにはフレームが無い)。`/youtubei/v1/player` のリクエストには、その応答を読むブリッジ自身の処理が付いている
- **watch pages only**: MutationObserver、scheduleApply、AudioContext の作成は、watch ページでだけ起きる — `/watch`、`/live/<id>`、配信を表示しているチャンネルのライブの URL (「A channel's live URL」を参照)
- **A channel's live URL**: `/@<handle>/live`、`/channel/<id>/live`、それより古い `/c/<name>/live`、`/user/<name>/live`、`/<name>/live` は、チャンネルが配信中の配信か、これから始まる配信を、URL で名指さずに表示する。ページの canonical リンクはそれを `/watch?v=<id>` として名指し、content.js と page-bridge.js の両方で、その id が「URL の指す動画」の役をする (`CHANNEL_LIVE_PATH` と `canonicalVideoId()`。2 つのファイルにミラーしてある)。canonical リンクは文書の head の中の、`ytInitialPlayerResponse` を代入するスクリプトより前にあるので、ブリッジの代入のフックは、その時点でもうそれを読める。チャンネルにどちらも無いときは、ページはチャンネル自身のページになる: canonical リンクはチャンネルを名指し、ページは watch ページではない
- **Saved per channel × type**: `gainLive` (配信 / アーカイブ) と `gainVideo` (動画 / Shorts / プレミア公開) は別々に管理する。videoType は `videoDetails.isLiveContent` だけから決め (`isLiveContent ? 'live' : 'video'`)、loudnessDb はこの決定に関わらない。ライブ配信とそのアーカイブは `isLiveContent=true` で live と数え、プレミア公開は `isLiveContent=false` なので video と数える
- **Accounting for YouTube's loudness normalization**: loudnessDb > 0 のとき、YouTube はすでに -14 LUFS まで減衰させている → effectiveLufs = -14。loudnessDb <= 0 のときは、そのままの値を使う
- **Do not resolve channel state until the migration finishes**: content.js は、起動時の旧形式の取り込みを `storageReady` として持ち、`applyPreferredGain()` はほかの何よりも先にそれを待つ。`applyAutomaticLoudnessGain()` も、`storageSettled` が false の間は false を返し、待つ側に回る。移行の前のマップは古い形式の「ゲインがあり、Auto のフラグが無い = Auto は OFF」で、これを今の規則 (フラグが無ければ全チャンネル共通の既定値) で解決すると、Auto がそれを引き取り、手動のゲインを計算したゲインで上書きする (ポップアップの `forceDetect` が取り込みより先に届いたときに起きる)
- **Resolve under the old rule while the fold has failed**: 成功したかどうかは `storageMigrated` に持ち、これが false の間、`resolveAutoApplySetting(..., unmigrated)` は「保存ゲインがあれば Auto は OFF」という古い規則を使う (options.js の一覧も同じ)。失敗を成功として扱うと、印もフラグも保存されないまま、Auto が手動のゲインを上書きする。`triggerApply()` は、`storageMigrated` が false の間、取り込みをやり直す (`foldInFlight` がやり直しを 1 つにまとめる)。1 回きりの書き込みの失敗は、次の適用で回復する
- **A bridge message stores nothing before the first apply for a URL**: `applyVideoVolume` は、最初の `applyPreferredGain()` がゲインを効かせたところで (その適用が始めた保存は待たずに)、その動画を `appliedVideoId` に入れる。それまでは、その URL の動画についてのブリッジのメッセージからは、Auto 自身の保存もライブの保存も行わない (`applyAutomaticLoudnessGain`、および `fromMessage` 付きの `applyPreferredGain` / `evaluateLiveSave`): URL が変わった後、その適用より前に届いたメッセージのとき、タブはまだ離れたページのチャンネルを持っていて、そこからの保存は、あるチャンネルのレベルを別のチャンネルのエントリへ保存することになる。ほかの経路 — ナビゲーション自身の適用、設定の変更、ポップアップを開くこと — は、前と同じく保存する
- **A settings change stores Auto's gain only where what Auto works out moved**: `autoLoudnessSettings` の変更はどれも、各タブでゲインを適用し直す。Auto 自身の保存とライブの保存がそれに続くのは、Target か全チャンネル共通の既定値が、そのタブが持っていた値から動いたときだけ (`applyPreferredGain(..., { stores })`)。表示単位やゲイン表示の変更は、何も保存しない
- **Auto's own save is made by a tab that is playing**: Auto によるゲインの保存とライブの保存は、ページの `<video>` が一時停止でもミュートでもないとき (`isVideoPlaying()`) にだけ行う。音量 0 とゲイン 0 は、再生中と数える。同じチャンネル・同じ種別でレベルの違う 2 つのタブは、ブリッジの返事のたび、設定の変更のたびに、それぞれ自分のゲインを保存していたので、保存ゲインは最後に届いたものになっていた。誰も聞いていないタブは、もうこれに加わらない。ゲインの適用はどちらの場合も行い、ページの `<video>` の `play` が `applyPreferredGain('play')` を走らせるので、適用の後で動画が再生を始めたタブは、そのときに保存する。再生中にページの `<video>` のミュートを解く `volumechange` も同じものを走らせるので、ミュートで始まった動画は、ミュートを解いたときに保存する。ミュートの状態は、動画ごとに、その最後の `play` か `volumechange` のときから持ち、スクリプトの開始の時点でページにあった動画については開始のときから持つ (`mutedSeen`)。ミュートの解除でない音量の変更は、何も適用しない
- **Do not save Auto's gain before the fold**: 取り込みの前にフラグなしのゲインを書くと、古い手動のゲインと同じ形になり、次の取り込みがそれを Auto OFF に固定してしまう。計算したゲインは再生には適用し、保存は `storageMigrated` が true になるまで待つ (手動の保存は、そのときの Auto の状態を明示のフラグとして書くので、取り込みの前でも見分けがつき、保存してよい)
- **The migration marker is taken in across tabs**: `storageMigrated` は、このタブ自身の取り込みの応答に加えて、`chrome.storage.onChanged` で届く `unifiedGains` でも true になる。正とする状態は、保存の側にある印: このタブの取り込みが失敗しても、別のタブが取り込みを終えていれば、それ以降の解決は今の規則に従わなければならない (古い規則のままにすると、別のタブが保存したフラグなしの Auto のゲインを手動のゲインと読み違え、そのタブでの手動の保存が Auto OFF を固定する)。content.js は同じイベントの中で解決し直し、options.js は一覧を描き直す
- **Deleting the legacy keys is not part of the migration**: `clearLegacyKeys()` が失敗しても、`migrateLegacyAutoGains()` は失敗にならない。印とゲインはすでに保存されていて、残ったキーは誰も読まない。ここで失敗を返すと、呼び出し側が古い規則に戻ってしまう。残りは、次の呼び出しが片付ける
- **Storage migration**: 古い `{ gain }` の形から `{ gainLive, gainVideo }` への自動の移行。`migrateLegacyAutoGains()` は、プロファイルごとに 1 回、起動時に走り、フラグの無い保存ゲインに明示の OFF を記録して、古い判定 (保存ゲインがあれば暗黙の OFF) を保存する。`autoLoudnessFallback:<channelId>:<type>` / `autoLoudnessFallbacks` があるときは、Auto が ON の種別の、覚えた値をゲインに取り込み、キーを消す。走ったことの印は、トップレベルの `unifiedGains` キー (Auto もフラグなしでゲインを書くので、2 回目の走行は Auto の覚えた値を明示の OFF に固定してしまう。設定のオブジェクトの中に置くと、移行の前に取った読み取りから出された設定の書き込みが、印を消す)。行き先の無い `@handle` のエントリは、author の名前で突き合わせる埋め戻しで UC にまとめる (ID の形に基づく移行は、SPA ナビゲーションのときにチャンネルをまたいだ破損を起こすので外した)
- **One channel ID form**: `detectChannel()` は UC の形だけを返す。DOM の `@handle` のリンクは、SPA ナビゲーションの間に古くなる (前のチャンネルを指す) ので、見分ける値としては受け付けない。page-bridge.js の `videoDetails.channelId` (UC の形) が代わりの出所になる。`meta[itemprop="channelId"]` という代わりの出所とブリッジの `channelId` は、どちらも `isChannelId()` (`UC` の後に `[A-Za-z0-9_-]` が続く) に合わせさせる
- **A bridge message is taken field by field**: ページの MAIN world で走るスクリプトなら、どれでもブリッジの `__yt_channel_volume__` メッセージを送れて、`event.source === window` は、ブリッジのときと同じくそれにも成り立つ。content.js は、`loudnessDb` を有限の数のときだけ、`liveLkfs` を `LEVEL_FLOOR_LKFS` より上の有限の数のときだけ、`baseLoudnessDb` を数のときだけ、`isLiveContent` を真偽値のときだけ、`author` を文字列のときだけ、`channelId` を UC の形のときだけ取る。別の型の項目は、無いものとして数える。これは、ブリッジとページの別のスクリプトを見分けない: 型の合ったメッセージは、どちらからでも取る
- **The worker refuses a write that does not describe a channel**: `CHANNEL_WRITES.saveChannelGain` / `saveChannelAutoApply` / `adoptHandleEntry` は、`channelId` が UC の形でないとき、`url` があって文字列でないとき、`gain` が 0 から 6 の範囲の有限の数でないとき (`isStorableGain`)、`authorName` が文字列でないとき、マップを読む前に `WriteRefused` (core/common.js) を投げる。名前は `applyEntryName` ([channel-volume-core](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#stored-map)) が当てはめ、名前の無い行は ID を取る。background.js は `createWriteListener` ([channel-volume-core](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#writes)) を通して答える。チャンネルの書き込み自身の失敗は `'storage-update-failed'`、設定の保存自身の失敗は `'settings-update-failed'` で、どの書き込みも名指していないメッセージは `[YTCV] unknown message type` として記録する。`deleteChannel` は、空でない文字列ならどのキーでも取る (`isRowKey`)。マップがまだ古い `@handle` のキーを持っているため
- **Choosing the channel display name**: ブリッジの `videoDetails.author` が正とする出所 (今の動画のプレイヤーの応答から来るので、SPA ナビゲーションの後も正しい)。DOM の `getChannelDisplayName()` は代わりの出所でしかない (古いことがある)
- **YouTube reference = -14 LUFS**: `contentLUFS = -14 + loudnessDb`
- **Default target = -18 LUFS**: ユーザーが設定できる (-30 から -6 LUFS)
- **createMediaElementSource**: `<video>` 1 つにつき 1 回呼ぶ。もう一度は呼べない — ほかの拡張機能とぶつかる
- **Channel ID formats**: `UC...` (canonical) が正規の ID。`detectChannel()` は `@handle` を受け付けず、UC だけを返す。DOM に UC が無いときは、ブリッジの `videoDetails.channelId` を待つ。SPA ナビゲーションの後は、DOM に何があってもブリッジを待つ: `applyVideoVolume` が `detectChannel()` に尋ねるのは、その文書の最初の動画のときだけ。ナビゲーションの途中のページは、離れた動画のチャンネルをまだ名指していることがあるため
- **The popup asks; the page tells it nothing**: content.js はポップアップにメッセージを送らず、ポップアップは、1 秒ごとの問い合わせに返ってきたものを描く。ブリッジのメッセージのレベルから決まるゲインを、保存ゲインの経路で求めている間は、ポップアップの `getState` には、そのメッセージの前の状態で答える (`holdPopupStateWhile`)。だから、新しいレベルが、その前のゲインの隣に描かれることはない
- **Cross-tab sync**: `chrome.storage.onChanged` が `channelVolumes` の変更を届ける。チャンネルごと・種別ごとの自動適用のフラグと、種別ごとのゲインはすぐに反映し、ほかのタブでの削除は 1.0 に戻す
- **Channel-independent settings sync**: `autoLoudnessSettings` — Target LUFS、表示単位、ゲイン表示、2 つの Auto の既定値。どのチャンネルにも属さないもののすべて — は `chrome.storage.sync` に置く: ユーザーが Chrome の同期を ON にしていれば、Chrome は、そのユーザーがログインしているすべての Chrome とそれを同期するので、どの Chrome も同じ設定を読む。同期が OFF のとき、この領域は `chrome.storage.local` と同じように動く。チャンネル、移行の印、古い形式のキーは local に残す: `channelVolumes` はチャンネルごとのもので、チャンネルを保存するたびに大きくなり、sync の割り当て (1 項目 8 KB、全体で 100 KB、1 分に 120 回の書き込み — Auto は動画ごとに保存する) を超えてしまう。読む側はどれも `readSettings()` ([channel-volume-core](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#settings)) を通るので、worker がまだ移していないプロファイルは、自分が保存した設定を読む。その、sync の 2 回目の読み取りが、ここで効く: 2 回の読み取りが設定を移す処理をまたいだところで `{}` と答えると、content.js には既定値が、旧形式の取り込みには OFF の Auto の既定値が渡り、Auto が覚えたゲインが落ちる。content.js が `loadSettings()` の読んだものを当てはめるのは、読み取りを出してから `settingsRevision` (同期された設定の変更のたびに進む) が動いていないときだけなので、その間に届いた変更が、古い読み取りで取り消されることはない。`moveSettingsToSync()` ([channel-volume-core](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#settings)) は、worker の起動のたびに background.js の先頭で走るので、sync が拒んだ移動は、次の起動でもう一度試される。options.js は自分では設定を書かない: 変わった 1 項目を付けて `store:saveSetting` を送り、worker の `SETTINGS_WRITES.saveSetting` が、その項目を `SETTING_FIELDS` と照らして確かめ (知らない項目や、持てない値は `invalid-mutation`)、`readSettings()` が返すものに混ぜて `chrome.storage.sync` へ書く。だから、移す前に行われた保存は、local の残りの設定を一緒に運ぶ。options.js は `change` で保存し、`input` では決して保存しない。これで、スライダーは書き込みの割り当ての中に収まる。Chrome は領域ごとに 1 つの `onChanged` を発火する: content.js と options.js は、`autoLoudnessSettings` を `sync` の領域からだけ取り — 移す処理による削除は、`newValue` の無い `local` の変更として届き、それを取るとすべての設定が既定値に戻る — `channelVolumes` / `unifiedGains` を `local` からだけ取る。移す処理は、sync を書く前に sync を読むので、その間に届いた設定の保存は、local の古い写しに戻されてしまう。そこで、移す処理とすべての保存は、worker の `queueSettingsWrite()` の上で 1 つずつ順に走る。だから、移す処理が出ている間に届いた保存 — 最初の起動の移動のときや、失敗した移動の後の、後の起動の移動のときで、設定画面がそれ以来開いたままのとき — はそれを待ち、保存が出ている間に始まった移動は、その保存を待つ。background.js は、移す処理を `settingsMoved` としても持ち、それが決着してからだけ `migrateLegacyGains` に答える。だから options.js は、自分が話している worker の最初の移動の後にだけ、操作を出す。失敗した移動も、決着したものに入る: そのとき保存は sync へ書き、次の移動は、sync が設定を持っているのを見つけて、local の写しを落とすだけになる。ユーザーがログインしていて Chrome の同期が ON の 2 つの Chrome が、どちらも更新の前に設定を持っていたとき、先に移したほうがアップロードし、2 つ目は sync が運んできたものを持ち続ける。sync がどちらも運ぶ前に両方が移したときは、Chrome の同期が最後に取ったものを、両方が読む
- **The service worker is the sole writer of channelVolumes (and of the settings)**: content.js と options.js は、読んで変えて書く処理を自分ではせず、`chrome.runtime.sendMessage({ type: 'store:<op>' })` で background.js に頼む。`channelVolumes` は 1 つのキーの下にマップの全体を持つので、いくつものタブが同時に読んで書き戻すと、ほかのチャンネルのエントリが落ちる — 最後の書き込みが勝つ (Auto は動画ごとに保存するので、その重なりは日常のこと)。worker は `updateChannelVolumes()` の promise の連なりの上で順に処理し、移行は、列の中でマップを読み直すので、走っている間に保存されたゲインを巻き戻さない
- **NaN/Infinity guard**: 有限でないゲインの計算結果は 1.0 にする
- **Lazy audio chain**: ゲインが 1.0 (素通し) のときは `createMediaElementSource` を呼ばない → Live Caption のちらつきを避ける。`connectedVideo` (音声の経路) と `_lastProcessedVideo` (検出した動画) は別々に管理する
- **triggerApply design**: `setTimeout` の debounce をやめ、非同期の mutex (`_applyRunning`) が同時の実行を防ぐ。各きっかけ — `yt-navigate-finish` / `popstate` / `visibilitychange` / observer / 最初の読み込み — から直接呼ぶ。バックグラウンドのタブのスロットリングにも、ライブチャットの高頻度の DOM の更新にも影響されない
- **Gain overlay**: `.ytp-volume-area` にゲインの値を出す。SPA ナビゲーションでの DOM の作り直しも扱う — すでに作った要素を新しい volume area に追加し、置き換えられた volume area から移す (そこで作り直す方法だと、誰も見ていないプレイヤーに古い要素が残る)
- **Do not swallow failures**: メッセージの処理は `handleMessage()` を try/catch で包み、`respondOnce()` を通してちょうど 1 回答える (1 回きりのメッセージへの 2 回目の `sendResponse` は、Chrome 自身が捨てる — この絞り込みは、1 回だけ答えることを呼び出しの場所で読めるようにするもので、それを強制するものではない)。`commitGain()` は promise の連なりより先に同期で走り、`createMediaElementSource` は、ほかの拡張機能がその `<video>` を持っている間は例外を投げるので、promise だけを見ている catch では、返事が出ないままになる。非同期の側 (`forceDetect` の `sendDetectedState`) は、成功も失敗も、その同じ `respondOnce` につなぐ (返事が無いと、ポップアップは初期化中のまま固まる)。失敗は `reportFailure()` を通してコンソールへ出す。Auto のゲインの保存の失敗は、鳴っているゲインを変えないので、`applyPreferredGain` の中で受け止め、呼び出し側 (`forceDetect` の返事の経路) には渡さない。誰にも頼まれていない書き込み — Auto 自身の保存、handle のエントリの引き取り、旧形式の取り込み — は、代わりに `nameUnaskedWrite()` を通して名指す: 次の動画、次のナビゲーション、次の適用が同じ書き込みをもう一度行うので、続けて起きる失敗の始まりは info (Chrome が拡張機能のエラーの一覧に入れない) へ出し、error は、別の失敗の後に失敗した書き込みのために残す。**名前ごとに、自分の失敗の続きを持つ。** 1 つのブリッジのメッセージは、Auto の保存より先に引き取りを送る。すでに UC のエントリを持つチャンネルでは、引き取りは何も書かずに ok と答えるので、失敗の続きを名前どうしで共有すると、メッセージのたびにその答えで続きが終わり、Auto の保存は、どれだけ長く失敗し続けても報告されなくなる。届いた書き込みは、自分の名前の続きを終わらせる。視聴者が頼んだ書き込みは `reportFailure()` のままで、ポップアップ自身のメッセージがそれに添う
- **A gesture is made against a state, and applies to that state alone**: content.js の返事はどれも `appliesTo` を運ぶ — チャンネル、videoType、URL の指す動画。数えたものではなく状態から導くので、進める印は無い。動画が入っているのは、1 つのチャンネルの中でのナビゲーションが、チャンネルと種別はそのままで、ポップアップが表示するもの — 何より Content Loudness — を変えるからで、ポップアップの 1 秒ごとの問い合わせには、そのナビゲーションで移った先の `appliesTo` で答える。ポップアップは、スライダー、プリセット、Auto のトグル、「チャンネルに適用」と一緒にそれを送り返し、状態が先へ進んだ操作は、入れ替わった状態に適用せずに、`state moved` で断る。手元のチャンネルが、URL の指す動画について名指されていない間 (`currentChannelVideoId`。ブリッジのメッセージがある動画のチャンネルを名指したときと、適用がページからチャンネルを取ったときに入る) に行われた操作も、どれも同じく断る: SPA ナビゲーションの後、タブは、新しい動画の URL と一緒に前のチャンネルを持っていることがあり、そのときに描き直されたポップアップは、そうしなければ、それに合う状態を送り返してしまう。これが無かったとき、ハンドラーは、チャンネルをメッセージから取り、ほかのすべて — 名前、url、種別の枠、保存のときに固定する Auto の状態、Auto が ON の間に断る鍵 — を、操作が届いたときにタブが持っていたものから取っていた。そのため、SPA ナビゲーションの最中に離したスライダーが、あるチャンネルのゲインを、3 つ目のチャンネルの名前で、別のチャンネルのエントリへ書いた。プレビュー (`setGainLive`) もこれを運ぶので、断られることになる操作がレベルを動かすことはない。状態が動く前に受け付けられたプレビューは、離したときの保存が断られると、`restoreGainAfterFailedSave()` が元に戻す
- **A slider preview holds the gain until its gesture ends**: 受け付けられた `setGainLive` は、その `appliesTo` についてのプレビューを始める。`currentGestureState()` がまだそれと等しい間、ほかのどこかから来たゲイン — ブリッジのメッセージ、別のタブの書き込み、設定の変更、ライブの追従 — は `commitGainFromElsewhere` を通る (ライブのゲインは `commitLiveGain` を通る)。これは、鳴っているゲインをそのままにして、ページが今再生している要素にそれをもう一度設定するので、プレビューの最中に作り直されたプレイヤーも、そのゲインでつながる。ポップアップは、スライダーの上でポインターかキーが押されたままの間、プレビューをもう一度送る (`holdPopupSlider`、[channel-volume-core](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#sliders)) ので、押されたままの操作は終わらない。操作は、`setGain` が届いたとき、または最後に受け付けられたプレビューから `PREVIEW_IDLE_MS` (2 秒) が過ぎたときに終わる。保存なしで終わったときと、プレビューの後で保存が断られた後は、`applyPreferredGain()` が、そのとき保存にあるものを適用する。これが無かったとき、ドラッグの最中に届いた適用が、視聴者の指の下で保存ゲインを戻し、離したときにそちらが保存されることがあった
- **A manual gain is a gain only once it is saved**: 保存が失敗すると、`setGain` / `applyLoudness` は、`restoreGainAfterFailedSave()` に、`applyPreferredGain()` を通して保存済みの値を読み直して適用させ、それが終わってから `{ ok: false }` を返す。スライダーは `input` のときに `setGainLive` でもうプレビューしているので、「前の値」は保存されていない新しい値になっていて、メモリの中の写しでは戻せない。戻さないと、鳴っている音量と保存済みの値が食い違い、ポップアップは、失敗の後に読み直した値を表示するので保存されたように見え、次のナビゲーションがそれを戻す
- **Reflect the saved values before showing the screen**: popup と options は、読み込み中の画面を `body.initializing` で隠し、保存済みの設定を描いたところでそれを外す (options は、読み込みが失敗したときも外す — 隠れたままの画面は、操作もできない)。初期化中は、`body.initializing *` (と `::before` / `::after`) の `transition: none !important` がトランジションを止める — セレクターを並べ上げる方法では、誰かが書き忘れたコントロールが漏れ、`!important` が無いと、個別のセレクターが詳細度で勝つ。トランジションは値が書かれた瞬間に走り始めるので、残りが画面の上で動き、「表示してから更新した」ように読める。`revealPage` ([channel-volume-core](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#pages)) は次のフレームでクラスを外すので、トランジションは、書かれた値から始まる
- **Claim nothing about what was not read**: options の最初の読み取りは、`autoLoudnessSettings` (sync。`readSettings()` を通す) と `channelVolumes` (local) を 1 つの `Promise.all` で取る。2 つのうち片方だけが成功した状態を作らないためで、失敗のときに出す `settingsLoadFailed` の行は、その 1 回の読み込みを指す。その文言は、読み取りと次の行動 (再読み込み) だけを述べ、画面の値については何も言わない — 読み取りの最中に届いた変更通知は、失敗が分かる前に描かれるので、値を述べる文言は偽になりうる。失敗が決着した後の変更通知は取らない (別のタブからの書き込みが、再読み込みを求めている画面に乗ってしまう)。決着する前に届いた通知は、もう画面にあり、そのまま残る
- **Do not let anything be operated that was not read**: 設定の操作 (Target LUFS / 2 つの Auto の既定値 / 表示単位 / ゲイン表示) と、壊す操作 (全削除、行の ×) は、マークアップの中で無効にして出荷し、読み取りを終えた読み込みがそれらを有効にする。`saveSetting` も、`settingsLoaded` が false の間に行われた書き込みを断る — マークアップが最初の断り、ハンドラーがその後ろの断り。行の × は、描画がそのときの状態で書くので、成功した読み込みの次の描画で有効になる
- **The first read loses to a change that arrives after it**: 読み取りは変更通知より先に出され、出されたときの値を返す。`loadAll` は、get の前に `settingsRevision` / `channelRevision` を記録し、読んだものを、動いていない側にだけ当てはめる。変更通知は、その種類のリビジョンを 1 つ進め、チャンネルの側は、通知が運んだ `newValue` を描いて持つ (読み直すと、最初の読み取りと競う 2 回目の読み取りになる)。設定の側は、差分ではなくオブジェクトの全体を当てはめる — 一部だけを当てはめると、触れなかった項目が、リビジョンのガードの下でマークアップの既定値のまま残る
- **`renderChannels` is render-only**: 渡された一覧を描き、保存は読まない。何も持っていなければ、何も描かない。自分の書き込み (行の削除、全削除) の後にも読み直さない — service worker の書き込みは変更通知として戻ってきて、その通知が一覧を運び、描き直しを起こす
- **A row is shown and sorted under one label**: 並べ替えも名前のセルも `rowLabel()` ([channel-volume-core](https://github.com/semnil/channel-volume-core/blob/main/docs/shared-files.ja.md#stored-map)) を使う。名前の無いエントリや、名前が文字列でないエントリは、ID の下に並び、その × で削除できる
- **Showing an invalidated context**: この拡張機能を再読み込みして content.js の `chrome.runtime` が無効になると、ポップアップからの `chrome.tabs.sendMessage` は `Receiving end does not exist` で reject される。Web Audio API と DOM のオーバーレイは `chrome.*` に頼らないので、前に適用したゲインの表示は画面に残り、誤解を招く。ポップアップの catch 節は、「チャンネル未検出」ではなく `reloadPageNeeded` をステータスの行に出し (ja: 「拡張機能と接続できません。ページを再読み込みしてください (F5)」)、ユーザーに F5 を押すよう促す。設定の読み取りが失敗したポップアップも `reloadPageNeeded` を出し、タブには何も尋ねない。あるタブの content script が切り離されているかどうかを見分けるには、DevTools のコンソールの実行コンテキストをこの拡張機能の content script に切り替えて、そこで `chrome.runtime?.id` を読む: そこで `undefined` なら切り離されていて、ページの再読み込み (F5) で戻る。ページ自身のコンテキストでは、この値はどちらの場合も `undefined` になる
